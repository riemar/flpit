# M27: `rank` / `rank_by`

## 1. Goal
Leaderboards and percentile buckets need "the rank of each element, in the original order". Python has no stdlib rank (users pull in pandas/scipy for `rankdata` or hand-roll `sorted(set(...))` + dict). MoreLINQ's `Rank`/`RankBy` yield a **dense** rank per element in source order, **descending by default** (the largest value has rank 1). Niche (Phase 4), but small once ordering helpers exist.

## 2. Scope
**In:** `rank(*, descending=True)` and `rank_by(key_selector, *, descending=True)` on `_LinqOps`.
**Out:** other ranking methods (competition "1224", ordinal, fractional): not in MoreLINQ; a `method=` keyword can follow if asked. Comparer overloads (D3).

**MoreLINQ overload mapping**
| MoreLINQ | flpit |
|---|---|
| `Rank()` | `rank()` |
| `Rank(IComparer<T>)` | omitted (D3); the common use, reversing the order, is `rank(descending=False)` |
| `RankBy(keySelector)` | `rank_by(key_selector)` |
| `RankBy(keySelector, IComparer<TKey>)` | omitted (D3); reverse with `descending=False`, custom orders through the key |

## 3. Detailed design
### 3.1 Signatures
```python
def rank(self, *, descending: bool = True) -> FlpIt[int]: ...
def rank_by(self, key_selector: Callable[[TItem], Any], *, descending: bool = True) -> FlpIt[int]: ...
```
### 3.2 Semantics
- Kind: intermediate, deferred. Buffering: full (the source is materialised at the first `next()`). Short-circuit: none.
- Output: one `int` per source element, in source order. Ranks are **dense** and start at 1: equal keys share a rank, the next distinct key gets the next integer (`[10, 30, 20, 30]` → `[3, 1, 2, 1]`).
- Direction: `descending=True` (default, as MoreLINQ) gives rank 1 to the largest key; `descending=False` to the smallest. The keyword replaces the comparer overloads' main use (D3).
- Keys: `rank()` uses the element itself. `key_selector` is called **exactly once per element**, in source order.
- None keys sort lowest (same `_none_aware_key` rule as `order_by`), so with the default direction they get the largest rank number.
- **Intentional deviations from MoreLINQ** (README entry):
  1. MoreLINQ de-duplicates by **item** equality (`Distinct()` on the elements) and then orders the distinct items by key, so two *different* items with the *same* key get *different* ranks depending on source order (`["bob", "al", "eve", "x"].RankBy(len)` gives `[1, 3, 2, 4]`). flpit ranks by key, so equal keys always share a rank: `[1, 2, 1, 3]`. Results are identical whenever the key is injective on distinct items, which includes `rank()` itself.
  2. MoreLINQ calls the key selector once per distinct item; flpit once per element.
  3. MoreLINQ throws `ArgumentNullException` for `null` elements (they are dictionary keys); flpit accepts `None` elements (only keys are compared).
  4. flpit does not require elements to be hashable (MoreLINQ uses them as dictionary keys); keys only need ordering and equality.
- Validation (eager): `key_selector is None` → `ArgumentNoneError("key_selector")`; `descending` must be a `bool` (`TypeError` otherwise, prevents `rank_by(k, "desc")` silently meaning True).
- Incomparable keys raise `TypeError` at enumeration. Empty source → empty.
- Re-enumeration re-materialises the source.

### 3.3 Implementation sketch
```python
def rank_by(self, key_selector, *, descending=True):
    _require_callable(key_selector, "key_selector")
    _require_bool(descending, "descending")
    src = self._source()
    def _generator():
        keys = [key_selector(x) for x in src]
        yield from _dense_ranks(keys, descending)
    return FlpIt(_FactoryIterable(_generator))

def rank(self, *, descending=True):          # same, with keys = list(src) and no selector calls

def _dense_ranks(keys, descending):          # module-level
    try:
        distinct = set(keys)                 # fast path: hashable keys
    except TypeError:
        distinct = None
    if distinct is not None:
        ordered = sorted(distinct, key=_none_aware_identity, reverse=descending)
        rank_of = {k: r for r, k in enumerate(ordered, 1)}
        return map(rank_of.__getitem__, keys)
    order = sorted(range(len(keys)), key=lambda i: _none_aware_identity(keys[i]), reverse=descending)
    ranks = [0] * len(keys); r = 0; prev = _MISSING
    for i in order:                          # fallback: unhashable keys, adjacent-equality walk
        if prev is _MISSING or keys[i] != prev:
            r += 1; prev = keys[i]
        ranks[i] = r
    return iter(ranks)
```
- Fast path: O(n + d log d) time (d = distinct keys), O(n) memory. Fallback: O(n log n). Both paths must agree on hashable inputs; a Hypothesis test checks it by forcing the fallback.
- Prototype at 1e5 ints with 1,000 distinct values: index-sort-only version 35 ms vs the dict idiom 5 ms, which is why the hashed path is primary.
- **FlpList fast path:** none (the work is the sort, not the access).

## 4. Tests
- **Ported:** none (D7, 0 % by design); MoreLINQ's 12 cases (laziness, null comparer, descending/ascending series, all-equal, grouped duplicates, highest rank is 1, key selector, custom comparer) are a checklist; the custom-comparer case becomes a `descending=False` test. Skip categories: n/a.
- **Own unit tests** (`tests/unit/morelinq/test_rank.py`, both `flp_type`s):
  - Descending series → `1..n`; ascending series → `n..1`; all equal → all 1; three concatenated copies of `range(10)` → 10 distinct ranks repeated.
  - `descending=False` mirrors; highest-ranked element has rank 1 in both directions.
  - `rank_by(len)` on `["bob", "al", "eve", "x"]` → `[1, 2, 1, 3]` (pins deviation 1); key-selector call count = n.
  - None keys rank last (descending) / first (ascending); None elements accepted by `rank_by`.
  - Unhashable keys (`rank_by(lambda x: [x])`) use the fallback and equal the hashed result (Hypothesis, lists of small ints).
  - `rank_by(None)` → `ArgumentNoneError`; `descending="no"` → `TypeError`; both eager.
  - Deferral (`NoIterList`), re-enumeration, one-shot.
- **Contracts** (auto): deferral, lazy key selector, full buffering, FlpList not mutated.
- **Typing** (`tests/typing/test_types_rank.py`): `assert_type(flp.it(["a"]).rank_by(len), FlpIt[int])`, `assert_type(flp.lst([1]).rank(), FlpIt[int])`; `descending` is keyword-only (positional call is a type error).

## 5. Differential harness
`difftest/specs/rank.toml`, `rank_by.toml`; oracle `Operators/Rank.cs` calling `MoreEnumerable.Rank/RankBy` statically; `descending=False` maps to `Comparer<T>.Create((a, b) => b.CompareTo(a))` on the .NET side (oracle-only use of a comparer to reach the same semantics).
- Items: empty, singleton, all equal, `range(0, 20)` shuffled with duplicates, strings, ints with nulls in the **key** but not in elements for MATCH domains.
- Key selectors: `identity`, `mod(k)`, `key_len`.
- Probes: values, `trace` (selector calls).
- Expected: MATCH when the key is injective on distinct items (`identity`; `mod(k)` over items `< k`). `EXPECTED_DIFFERENCE` (reason: "OTHER: dense rank by key vs MoreLINQ rank by distinct item", README) for non-injective keys and for selector-call counts with duplicate items. `null` elements: `EXPECTED_DIFFERENCE` (MoreLINQ throws).

## 6. Benchmarks
`tests/benchmarks/test_bench_rank.py`, sizes 1e3 / 1e5, random ints in `range(1000)`:
- `native`: `r = {v: i for i, v in enumerate(sorted(set(data), reverse=True), 1)}; [r[v] for v in data]`

- Target ratio ≤ 1.3× (buffering default).

## 11. Risks / open questions
- Deviation 1 is a judgement call: exact MoreLINQ parity would require hashable elements and rank items, not keys, which surprises users ranking by a score. If parity is preferred, implement MoreLINQ's rule and flip the difftest classification; the tests above make the choice explicit either way.
- `_require_bool` is a new tiny helper; add it to F05's `_validation.py` (also useful for M28's `descending`).
- NaN keys order unpredictably (as with `sorted`); documented, not handled.
