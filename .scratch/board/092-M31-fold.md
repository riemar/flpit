# M31: `fold`

## 1. Goal
MoreLINQ `Fold` passes the elements of a sequence that must have **exactly N** elements as N arguments to a function: `"1,2,3".Split(',').Fold((a, b, c) => ...)`. Python already has argument unpacking (`a, b, c = xs`, `f(*xs)`), so the value is low; the operator is in the curated list for translation completeness and because, unlike unpacking, it stays fluent, stops reading after N + 1 elements and raises a descriptive, catchable error. The card's main job is choosing a Python signature for MoreLINQ's 16 arity overloads.

## 2. Scope
**In:** `fold(count, folder)` on `_LinqOps`; typed overloads for `count` 1..16 (MoreLINQ parity); new exception `SequenceCountError(ValueError)`; FlpList fast path.
**Out:** arity inference.

**Signature decision**
| Option | Verdict |
|---|---|
| `fold(folder)` reading the arity with `inspect.signature` | Rejected: fails or guesses for builtins without signatures, `*args`, defaults, `functools.partial`, C callables; the same "no magic on callbacks" rationale as D4 (explicit suffix methods instead of arity sniffing). |
| `fold(folder)` calling `folder(*all_elements)` with no count check | Rejected: loses the "exactly N" guarantee that is the operator's point, and reads unbounded input. |
| **`fold(count, folder)`** | **Chosen**: explicit, typed per arity through `Literal` overloads, bounded reads. |

**MoreLINQ overload mapping**
| MoreLINQ | flpit |
|---|---|
| `Fold<T, TResult>(Func<T, TResult>)` ... `Fold(Func<T x16, TResult>)` | `fold(1, f)` ... `fold(16, f)`; any `count >= 1` works at runtime, counts above 16 fall back to `Callable[..., TResult]` typing |

## 3. Detailed design
### 3.1 Signatures
```python
@overload
def fold(self, count: Literal[1], folder: Callable[[TItem], TResult]) -> TResult: ...
@overload
def fold(self, count: Literal[2], folder: Callable[[TItem, TItem], TResult]) -> TResult: ...
@overload
def fold(self, count: Literal[3], folder: Callable[[TItem, TItem, TItem], TResult]) -> TResult: ...
# ... one overload per arity up to Literal[16] (written out, like MoreLINQ's generated Fold.g.cs)
@overload
def fold(self, count: int, folder: Callable[..., TResult]) -> TResult: ...
def fold(self, count: int, folder: Callable[..., TResult]) -> TResult: ...
```
```python
class SequenceCountError(ValueError):            # flpit/core/errors.py, exported from flpit
    expected: int
    too_many: bool
```

### 3.2 Semantics
- Kind: terminal. Buffering: partial (at most `count + 1` elements). Short-circuit: yes.
- Pulls: at most `count + 1` elements. If element number `count + 1` exists, `SequenceCountError` is raised immediately without reading further (MoreLINQ throws while assigning that element). If the source ends first, the error is raised after the end is seen.
- Messages (MoreLINQ `FormatSequenceLengthErrorMessage`, kept verbatim for the harness): `Sequence contains too few elements when exactly 3 were expected.` / `... too many elements when exactly 1 was expected.`; thousands separator as in .NET `N0` (`{count:,}` → `1,000`).
- `folder` is called once, with the elements positionally in source order, and only when the count matches; its return value is returned unchanged; its exceptions propagate.
- Validation (eager, before reading): `count` via `_require_index`; `count < 1` → `ArgumentOutOfRangeError("count")` (MoreLINQ has no 0-arity overload); `folder` via `_require_callable` (`None` → `ArgumentNoneError("folder")`). No upper bound (16 is a C# arity artefact).
- None elements are ordinary arguments.
- One-shot source: at most `count + 1` elements consumed.
- `SequenceCountError` is a `ValueError`, so code that catches unpacking errors (`ValueError`) still works; it carries `expected` and `too_many` for programmatic use.

### 3.3 Implementation sketch
```python
def fold(self, count, folder):
    count = _require_positive(_require_index(count, "count"), "count")
    _require_callable(folder, "folder")
    items = list(islice(self._source(), count + 1))      # bounded read, C-level
    if len(items) != count:
        raise SequenceCountError(count, too_many=len(items) > count)
    return folder(*items)
```
- O(count) time and memory.
- **FlpList fast path:** `n = len(data)`; mismatch → raise the same error without iterating; else `folder(*data)`. Identical observable behaviour (lists have no pull side effects, same exception and message) and O(1) for the check; justified by the benchmark below.
- Overloads: 17 `@overload` stubs on the mixin (about 50 lines); acceptable boilerplate, generated once with a throwaway snippet and committed as plain code (no build step).

## 4. Tests
- **Ported:** none (D7, 0 % by design). MoreLINQ's 5 cases (too few, empty, too many, folds of 1..16 elements, laziness of the folder) are a checklist with own equivalents. Skip categories: n/a.
- **Own unit tests** (`tests/unit/morelinq/test_fold.py`, both `flp_type`s plus generator sources):
  - Folds for every count 1..16 (concatenate letters, as a table-driven test) and one count above 16 (20).
  - Too few (including empty) and too many: type `SequenceCountError`, `isinstance(e, ValueError)`, exact messages for count 1 (`was`) and 3 (`were`), `expected`/`too_many` attributes; `1,000` formatting for `count=1000`.
  - Pull count: on `itertools.count()`, `fold(3, f)` raises after pulling exactly 4 elements; folder never called.
  - Folder receives elements positionally in source order; folder exception propagates; return value passed through (including `None`).
  - Validation: `count` 0 / -1 → `ArgumentOutOfRangeError`; `None` → `ArgumentNoneError`; `folder=None` → `ArgumentNoneError`; all before reading the source.
  - FlpList fast path equals the generic path for matching, short and long lists.
- **Contracts** (auto): terminal, `short_circuit = true` with `contract_max_pull = 3`, FlpList not mutated.
- **Typing** (`tests/typing/test_types_fold.py`): `assert_type(flp.it([1, 2]).fold(2, lambda a, b: a + b), int)`; `fold(3, lambda a, b, c: str(a))` → `str`; a 2-parameter lambda with `count=3` is a pyrefly error (negative check); a non-literal `count` falls back to `Callable[..., R]`.

## 5. Differential harness
`difftest/specs/fold.toml`; oracle `Operators/Fold.cs` switches on `count` (1..16) and calls the matching `MoreEnumerable.Fold` overload with a folder that returns its arguments as an array (catalogue entry `args_tuple`, added here on both sides), so the comparison sees exactly which elements arrived in which position.
- `count ∈ {0, 1, 2, 3, 16, 17}`; items with lengths `count - 1`, `count`, `count + 1`, empty; ints, strings, ints with nulls; sources `counting`, `one_shot`, `throwing_at(i)`.
- Probes: result, exception type/message/timing, `trace` (count + 1 pulls on the too-many path).
- Expected: MATCH for counts 1..16. `count = 0`: both reject but differently (`ArgumentOutOfRangeError` vs no such overload): `UNCOMPARABLE` (reason: "no 0-arity Fold overload in MoreLINQ"). `count = 17`: `UNCOMPARABLE` (reason: "MoreLINQ stops at 16 arguments").
- Exception mapping: MoreLINQ `InvalidOperationException` ↔ `SequenceCountError`, compared by message (testplan §27).

## 6. Benchmarks
`tests/benchmarks/test_bench_fold.py`: the operator is O(count) with tiny counts, so the benchmark folds many small sources; sizes 1e3 / 1e5 = number of 3-element sources, `f = lambda a, b, c: a + b + c`:
- `native`: `[f(*t) for t in triples]` with an `a, b, c = t` length check (the unpacking idiom).
- `flpit-FlpList`: `[s.fold(3, f) for s in flplists]` (pre-built FlpLists, fast path); `flpit-FlpIt`: `[flp.it(t).fold(3, f) for t in triples]`.
- Target ratio ≤ 2.0× for FlpList (method-call and validation overhead dominate at this size), ≤ 3.0× for FlpIt (wrapper + `islice`). Recorded, not gating (D8).
